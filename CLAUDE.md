This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

TestFlow Agent converts plain-English manual QA test cases (and/or live browser-recorded API traffic) into reusable API automation assets: Postman collections, Playwright API tests, and JMeter `.jmx` plans. It also executes the enrollment flow live against a mock API. See `README.md` for the full feature/demo narrative.

## Commands

```bash
# Start all three services (each in its own terminal)
node mock-enrollment-api/server.js   # http://localhost:4000
node backend/server.js               # http://localhost:5001 (or: npm --prefix backend run dev for nodemon)
npm --prefix frontend run dev        # http://localhost:5173

# Frontend build/lint
npm --prefix frontend run build
npm --prefix frontend run lint
```

There is no automated test runner configured yet. `mock-enrollment-api/package.json` has the default placeholder `npm test` script and it intentionally exits with an error — do not "fix" this unless asked.

## Architecture

Three independent local services, no shared build:

- `frontend/` — React (Vite) dashboard. Nearly all UI state and logic lives in `frontend/src/App.jsx` (manual test case input, detected flow, generated artifacts, live discovery panel, execution results, toasts). It talks directly to hardcoded local URLs: `http://localhost:5001/agent`, `http://localhost:5001/discovery`, and `http://localhost:4000`.
- `backend/` — Express API, the real core of the system.
  - `backend/server.js` is thin: mounts `backend/routes/analysisRoutes.js` at `/agent` and `backend/routes/discoveryRoutes.js` at `/discovery`.
  - `backend/lib/analysisHelpers.js` is the manual-scenario engine: `parseScenario()` is the single source of truth for inferring state/plan/effective date/positive-vs-negative intent from free text, and `buildEnrollmentFlow`/`buildPostmanResponse`/`buildPlaywrightResponse`/`buildJmeterResponse` generate the aligned outputs from that scenario.
  - `backend/services/discoveryService.js` implements the live browser-recording flow: launches headed Chromium via Playwright, records a HAR (`generated/discovery-session.har`), then classifies/sanitizes/correlates captured requests into `capturedApis`, `dynamicVariables`, and `detectedSteps`.
- `mock-enrollment-api/` — in-memory Express service exposing the fixed sequence `/auth/token -> /members -> /plans -> /enrollments -> /enrollments/:id`. State (tokens, members, enrollments) lives only in process memory and resets on restart.

### Two ways a flow gets generated

1. **Manual scenario path**: frontend posts free text to `/agent/analyze`; `parseScenario()` normalizes it and every generator endpoint (`/agent/generate-postman`, `/agent/generate-playwright`, `/agent/generate-jmeter-plan`, `/agent/run-enrollment-flow`) derives output from that same normalized scenario. Defaults: `TX`, `Silver`, `2026-01-01`. Accepts ISO or `MM/DD/YYYY` dates.
2. **Live discovery path**: user enters a base URL, hits Start Discovery (`POST /discovery/start`), performs the flow by hand in the opened headed browser, then Stop Discovery (`POST /discovery/stop`). The captured HAR is classified into business-relevant API calls and dynamic variables and displayed/generated from instead of the hardcoded enrollment flow. Falls back to the manual scenario path when no discovery session exists.

## Key Conventions

- Keep all four output types (Postman, Playwright, JMeter, `run-enrollment-flow`) in sync — they must represent the same business flow. Changing scenario semantics in one requires updating the others.
- The shared dynamic variable vocabulary: `baseUrl`, `accessToken`, `memberId`, `planId`, `enrollmentId`, `state`, and (positive-path only) `effectiveDate`.
- Backend endpoints accept `manualTestCase`, `manual`, or `text` interchangeably for the scenario body field — preserve this when extending payloads.
- Positive vs. negative scenarios diverge only at enrollment submission: positive includes `effectiveDate` and a validation step; negative "missing effective date" omits `effectiveDate`, expects HTTP 400, and skips the validate-enrollment call.
- Discovery classification/sanitization rules (in `discoveryService.js`) matter for generated-asset quality:
  - Dynamic-variable detection is *not* a fixed allow-list. A field is a candidate if its key is one of the "specific" names (`accessToken`, `token`, `refreshToken`, `memberId`, `customerId`, `employeeId`, `planId`, `enrollmentId`, `orderId`, `transactionId`, `leaveRequestId`, `csrfToken`, `sessionId` — always captured, name-preserving) **or** its key matches the generic pattern `/(^id$|Id$|_id$|Number$|_number$)/i` (e.g. `empNumber`, `customer_id`). Generic candidates named from a literal `id` key are named via `deriveGenericIdName`, which derives the name from the **immediate JSON parent key** wrapping the `id` (e.g. `employee.id` → `employeeId`, `leaveType.id` → `leaveTypeId`), falling back to the URL's last meaningful path segment only when the parent key is a generic wrapper (`data`, `items`, `results`, etc.) — it deliberately does **not** substring-match the whole URL path anymore, since on real apps almost every endpoint path contains words like "employees" regardless of what a given `id` field actually identifies.
  - When multiple candidates share a derived name (e.g. the logged-in admin's own `empNumber` vs. the *target* employee's `empNumber` — same field name, different entities), `detectDynamicVariables` picks the one with the highest **reuse score**, not just "first reused": a match that reappears as a URL path segment or exact query-param value scores far higher than one that merely coincides once inside an unrelated JSON blob, and identifiers returned by a mutating (POST/PUT/PATCH/DELETE) step's response always qualify as a candidate (so the ID of a just-created resource — e.g. a submitted leave request's own `id` — isn't crowded out by an earlier incidental list-read of the same entity type).
  - Reuse detection treats short values (<6 chars — most numeric IDs) differently from long ones: long values use a substring search; short values require a *whole-token* match (a full path segment, a full query-param value, or an exact JSON leaf value) so a short id like `"7"` isn't falsely matched inside an unrelated number. The same whole-token safety applies at *substitution* time — `replaceValueOccurrences` in `backend/lib/sanitize.js` is what both `analysisHelpers.js` and `discoveryService.js` use to template a detected value into `{{name}}`/`${name}`, and it never does a naive substring replace for short values (a port number like `4700` must not get corrupted by a reused id of `7`).
  - Identical repeated requests (same method/path/query/body, e.g. a page reloading the same widget twice) are deduped before generation (`dedupeIncludedApis`); the surviving step carries a `repeatCount` when it collapsed more than one occurrence. The raw, undeduped `capturedApis` list is still exposed in full for audit/display.
  - Exclude static assets, analytics/tracking, `i18n`/`messages`, and `/events/push` noise from captured APIs; only POST/PUT/PATCH/DELETE or JSON `/api/` traffic counts as business API.
  - `normalizeBaseUrl`/`normalizeLaunchUrl` reduce a full page URL to its origin for `baseUrl` — never use a full login-page URL as `baseUrl`.
  - Each captured step defaults to `expectedOutcome: 'as-captured'`, meaning its assertion in every generated format is the literal captured status code — a captured 4xx/5xx is asserted as "correct" unless overridden. `POST /discovery/session/overrides` lets the frontend mark a step `'success'` (assert 2xx range) or `'failure'` (assert 4xx/5xx range) instead; `resolveStatusAssertion` in `analysisHelpers.js` is the single place all three generators (Postman/Playwright/JMeter) branch on this.
- **Masking is capture-time-vs-display-time split, by design.** The internal session (`activeSession`/`lastCompletedSession`, what generation reads via `getCapturedDiscoverySession()`) keeps **real, unmasked values** — including credentials — because the generated Postman environment / Playwright defaults / JMeter variables are meant to be immediately runnable without the user manually filling in blanks. Masking (`buildMaskedApis` → `maskFormUrlEncodedString`/`sanitizeValue`/`sanitizeHeaders`, all in `backend/lib/sanitize.js`) is applied only in `buildSessionSummary`, i.e. only in what the **frontend UI displays** (`/discovery/session`, `capturedApis`/`includedApis` in the start/stop responses). Don't move masking back into the capture path (`normalizeHarEntry`/`parseMaybeJson`) — that would silently break runnability of the generated artifacts, which is the whole point of the discovery feature.
  - `extractCredentialValues` (in `discoveryService.js`, run in `stopDiscovery`) pulls the actual username/password/csrf value out of request bodies (JSON or form-urlencoded) so `getEnvironmentVariables` (in `analysisHelpers.js`) can populate the generated Postman environment / JMeter User Defined Variables with real values instead of blanks, and the Playwright builder can embed them as `process.env.X || <realValue>` defaults.
  - Session-bound values (CSRF tokens, cookies) are inherently short-lived and a raw captured token generally will **not** still be valid on a later run, since it's typically bound server-side to the session that was active when it was issued. Rather than relying only on the stale captured value, `findCsrfRefreshSource` (`discoveryService.js`, run in `stopDiscovery`) looks backward from the login/auth step for the nearest earlier HTML page response containing an extractable token (via `CSRF_TOKEN_HTML_PATTERNS`/`extractCsrfTokenFromHtml` in `backend/lib/sanitize.js` — a small ordered list of generic patterns: meta tag, hidden input, Vue-style attribute, generic JSON-ish assignment). When found, every generator prepends a **"Fetch Login Page (CSRF)"** step (`resolveCsrfRefreshStep` + `buildCsrfRefreshPostmanItem`/`buildCsrfRefreshPlaywrightBlock`/`buildCsrfRefreshJmeterBlock` in `analysisHelpers.js`) that re-fetches the login page and re-extracts a *fresh* token at runtime, so the collection/spec/plan can log in successfully on a rerun instead of just replaying a snapshot. Verified end-to-end against a live OrangeHRM login. The static captured value is still kept as the environment/default fallback for cases where no source page was found. The Playwright spec's header comment still notes that a `.env` override is available if this heuristic ever fails to match a given app's token-embedding convention.
  - JMeter's generated plan includes an `HTTPCookieManager` on the Thread Group (`buildCookieManagerBlock`) so the session cookie set by the login step is actually carried across all subsequent samplers — without it, JMeter (unlike Postman/Playwright, which handle this automatically) would drop the session and every step after login would 401.
- `backend/lib/sanitize.js` is shared between `discoveryService.js` (display-time masking) and `analysisHelpers.js` (generation-time templating) so the credential-field/masking/safe-substitution logic exists in exactly one place — don't reintroduce a second copy of that regex logic in either file.
- Generated artifacts use stable filenames: `testflow-enrollment-collection.json`, `testflow-enrollment-environment.json`, `enrollment-flow.spec.ts`, `enrollment-flow.jmx` (manual scenario) / `discovered-flow-collection.json`, `discovered-flow-environment.json`, `discovered-flow.spec.ts`, `discovered-flow.jmx`, `discovered-flow-data.json` (captured flow — the last one is a human-readable companion listing the same key/values already embedded in the JMX's User Defined Variables).
- The captured-flow Playwright builder (`buildCapturedPlaywrightResponse`) wraps each step's generated code in its own `{ ... }` block — every step declares locals with the same names (`stepUrl`, `stepHeaders`, etc.), so without block scoping the generated file doesn't compile. Preserve that block-wrapping if you touch this function.
- The frontend uses hardcoded local service URLs. If you introduce configurability, update analyze, generate, discovery, and run call sites consistently rather than just one.
- Keep UI changes incremental — preserve existing features and dashboard layout rather than redesigning it (see `instructions/phase1-live.md`, `instructions/phase2-har-fix.md` for the history/intent behind the discovery feature).
- Playwright MCP is registered in this repo's `.mcp.json` (`npx @playwright/mcp@latest`) — prefer it for UI debugging/validation. See `.claude/skills/verify-discovery/SKILL.md` for an end-to-end check of the discovery→generate pipeline specifically.
